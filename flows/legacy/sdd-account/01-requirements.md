# Requirements: Account Management

> Spec-Driven Development flow for Account and AccountRegistration classes.

## Overview

Account management provides immutable data representations for SIP account configuration and registration status. These are passive data objects with no business logic.

---

## Functional Requirements

### FR-1: Account Data Representation

**Description**: Account class SHALL represent SIP account configuration.

**Requirements**:
- FR-1.1: Account SHALL provide `getId()` returning account ID
- FR-1.2: Account SHALL provide `getURI()` returning SIP URI for registration
- FR-1.3: Account SHALL provide `getName()` returning full name
- FR-1.4: Account SHALL provide `getUsername()` returning SIP username
- FR-1.5: Account SHALL provide `getDomain()` returning domain (may be null)
- FR-1.6: Account SHALL provide `getPassword()` returning password
- FR-1.7: Account SHALL provide `getProxy()` returning proxy server
- FR-1.8: Account SHALL provide `getTransport()` returning transport protocol
- FR-1.9: Account SHALL provide `getContactParams()` returning Contact header parameters
- FR-1.10: Account SHALL provide `getContactUriParams()` returning Contact URI parameters
- FR-1.11: Account SHALL provide `getRegServer()` returning registration server
- FR-1.12: Account SHALL provide `getRegTimeout()` returning registration timeout
- FR-1.13: Account SHALL provide `getRegContactParams()` returning registration contact parameters
- FR-1.14: Account SHALL provide `getRegHeaders()` returning registration headers
- FR-1.15: Account SHALL provide `getRegistration()` returning AccountRegistration instance

**Source**: src/Account.js

---

### FR-2: AccountRegistration Data Representation

**Description**: AccountRegistration class SHALL represent registration status.

**Requirements**:
- FR-2.1: AccountRegistration SHALL provide `getStatus()` returning SIP status code (or null)
- FR-2.2: AccountRegistration SHALL provide `getStatusText()` returning human-readable status
- FR-2.3: AccountRegistration SHALL provide `isActive()` returning boolean registration state
- FR-2.4: AccountRegistration SHALL provide `getReason()` returning reason phrase
- FR-2.5: AccountRegistration SHALL provide `toJson()` returning plain object representation

**Source**: src/AccountRegistration.js

---

### FR-3: Immutability

**Description**: Account and AccountRegistration SHALL be immutable.

**Requirements**:
- FR-3.1: All properties SHALL be read-only (getters only, no setters)
- FR-3.2: Data SHALL only be set in constructor
- FR-3.3: No methods SHALL modify internal state
- FR-3.4: New instances SHALL be created for state changes

**Source**: Design pattern observed

---

### FR-4: Composition

**Description**: Account SHALL contain AccountRegistration via composition.

**Requirements**:
- FR-4.1: Account constructor SHALL create AccountRegistration from data
- FR-4.2: Account SHALL expose AccountRegistration via `getRegistration()`
- FR-4.3: AccountRegistration SHALL NOT be modifiable from Account

**Source**: src/Account.js constructor

## Non-Functional Requirements

### NFR-1: Performance

- NFR-1.1: Account object creation SHALL complete in < 1ms
- NFR-1.2: All getters SHALL execute in < 0.1ms

### NFR-2: Memory

- NFR-2.1: Account instances SHALL NOT create circular references
- NFR-2.2: AccountRegistration SHALL be garbage-collectable when Account is released

### NFR-3: Serialization

- NFR-3.1: AccountRegistration.toJson() SHALL return plain object
- NFR-3.2: Account SHALL NOT provide toJSON (implicit JSON.stringify behavior)

## Constraints

- C-1: Account depends on native data structure
- C-2: Password stored in plaintext (memory security consideration)
- C-3: No validation in getters (assumes valid constructor data)
- C-4: Domain and status may be null
