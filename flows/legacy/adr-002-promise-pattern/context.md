# ADR-002: Promise Pattern

> Architectural Decision Record for Promise-based async API over native callbacks.

**Status**: DRAFT  
**Date**: 2026-03-04  
**Level**: Enabling  
**Source**: Legacy analysis of src/Endpoint.js

---

## Context

The native PjSIP module uses callback-based async pattern:
```javascript
NativeModules.PjSipModule.method(args, (successful, data) => {
  if (successful) {
    // handle success
  } else {
    // handle failure
  }
});
```

Application code needs a cleaner async abstraction for:
- Chaining operations
- Error handling
- Integration with modern async/await
- Consistent API across all methods

---

## Decision

**Wrap all native callbacks in Promises.**

Pattern used throughout Endpoint:
```javascript
makeCall(account, destination, callSettings, msgData) {
  destination = this._normalize(account, destination);
  
  return new Promise(function(resolve, reject) {
    NativeModules.PjSipModule.makeCall(
      account.getId(), 
      destination, 
      callSettings, 
      msgData, 
      (successful, data) => {
        if (successful) {
          resolve(new Call(data));
        } else {
          reject(data);
        }
      }
    );
  });
}
```

Application usage:
```javascript
// Promise style
endpoint.makeCall(account, '100')
  .then(call => console.log('Call created:', call))
  .catch(error => console.error('Call failed:', error));

// Async/await style
try {
  const call = await endpoint.makeCall(account, '100');
  console.log('Call created:', call);
} catch (error) {
  console.error('Call failed:', error);
}
```

---

## Rationale

**Why Promises:**

1. **Modern JavaScript**: Promises are standard in ES2015+
2. **Async/Await Compatibility**: Enables async/await syntax
3. **Error Propagation**: Automatic error propagation through chain
4. **Composability**: Promise.all(), Promise.race(), chaining
5. **Readability**: Cleaner than callback nesting

**Why NOT alternatives:**

- **Callbacks**: Callback hell, harder error handling, not composable
- **Observables (RxJS)**: Overkill for simple async operations, additional dependency
- **Async Generators**: Not suitable for single-result operations
- **Direct callbacks**: Inconsistent with modern JavaScript practices

---

## Consequences

### Positive (+)

- ✅ Clean async/await syntax support
- ✅ Consistent error handling pattern
- ✅ Method chaining possible
- ✅ Integration with Promise-based APIs
- ✅ Better stack traces than callbacks

### Negative (-)

- ❌ Promise wrapping overhead (minimal, ~1ms)
- ❌ No cancellation support (native operations can't be cancelled)
- ❌ Rejection value is raw data, not Error objects (inconsistent error handling)
- ❌ No progress reporting (Promises are binary: pending/resolved/rejected)

### Neutral (○)

- ○ All methods return Promises (even simple operations)
- ○ Requires Promise polyfill for old environments (not needed for RN)

## Implementation Details

### Promise Wrapper Pattern

```javascript
return new Promise(function(resolve, reject) {
  NativeModules.PjSipModule.method(args, (successful, data) => {
    if (successful) {
      resolve(data);  // or resolve(new Class(data))
    } else {
      reject(data);   // Raw data, not Error object
    }
  });
});
```

### Error Handling Pattern

**Current**: Raw data rejection
```javascript
try {
  await endpoint.makeCall(account, '100');
} catch (error) {
  // error is raw data from native (string or object)
  console.error(error);
}
```

**Better** (not implemented): Error object wrapping
```javascript
if (successful) {
  resolve(new Call(data));
} else {
  reject(new SipError(data.code, data.message));
}
```

---

## Compliance

**This decision is ENABLELING.**

It enables application code to:
- Use async/await for SIP operations
- Chain operations with .then()
- Handle errors with .catch()
- Integrate with other Promise-based APIs

## Notes

**Legacy Observation**: All Promise rejections pass raw native data without wrapping in Error objects. This makes error handling inconsistent and type-unsafe.

**Recommendation**: Create SipError class hierarchy for consistent error handling:
- SipError (base class)
- SipRegistrationError
- SipCallError
- SipMessageError
