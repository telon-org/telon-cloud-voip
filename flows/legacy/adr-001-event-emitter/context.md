# ADR-001: EventEmitter Choice

> Architectural Decision Record for using Node.js EventEmitter in React Native context.

**Status**: DRAFT  
**Date**: 2026-03-04  
**Level**: Enabling  
**Source**: Legacy analysis of src/Endpoint.js

---

## Context

The react-native-sip2 library needs to emit events to application code when:
- Registration status changes
- Calls are received, changed, or terminated
- Messages are received
- Connectivity changes

React Native provides multiple event emission patterns:
- DeviceEventEmitter (native events)
- NativeEventEmitter (JavaScript event emitter for native modules)
- Third-party event emitters (mitt, eventemitter3)
- Node.js EventEmitter (from 'events' package)

---

## Decision

**Use Node.js EventEmitter from 'events' package** for the public API.

Endpoint extends EventEmitter:
```javascript
import {EventEmitter} from 'events'

export default class Endpoint extends EventEmitter {
  constructor() {
    super();
    // Subscribe to native events...
  }
}
```

Application usage:
```javascript
const endpoint = new Endpoint();
endpoint.on('call_received', (call) => { ... });
endpoint.on('registration_changed', (account) => { ... });
```

---

## Rationale

**Why Node.js EventEmitter:**

1. **Familiar API**: Node.js EventEmitter is well-known to JavaScript developers
2. **Rich Feature Set**: Supports multiple listeners, once(), removeAllListeners(), etc.
3. **Synchronous Emission**: Events emitted synchronously (predictable execution order)
4. **No Dependencies**: 'events' package is already a dependency (peer dependency of react-native)
5. **Type Safety**: Can be typed with TypeScript definitions

**Why NOT alternatives:**

- **DeviceEventEmitter**: Only for native-to-JS events, not for public API
- **NativeEventEmitter**: Overhead for pure JavaScript events
- **Third-party**: Additional dependencies, no significant benefit
- **Custom implementation**: Reinventing the wheel

---

## Consequences

### Positive (+)

- ✅ Familiar API for Node.js developers
- ✅ Multiple listeners per event supported
- ✅ Event listener management (on, off, once, removeAllListeners)
- ✅ Error event handling (if error listener registered)
- ✅ Synchronous, predictable event ordering

### Negative (-)

- ❌ Node.js pattern, not React Native pattern (potential confusion)
- ❌ Memory leak risk if listeners not removed (no cleanup in code)
- ❌ No backpressure handling (events emitted synchronously)
- ❌ Event names are strings (no type safety without TypeScript)

### Neutral (○)

- ○ Requires import from 'events' package
- ○ Endpoint must call super() in constructor

---

## Compliance

**This decision is ENABLELING.**

It enables application code to:
- Listen to SIP events via familiar EventEmitter API
- Add/remove listeners dynamically
- Use standard EventEmitter patterns (once, removeAllListeners)

## Notes

**Legacy Observation**: Event listeners are subscribed in constructor but never removed. This creates potential memory leak if Endpoint instance is discarded without cleanup.

**Recommendation**: Document that Endpoint should be singleton or provide destroy() method to remove listeners.
